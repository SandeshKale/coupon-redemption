# ADR-0002: Luhn mod 32 check character; the 0↔Z adjacent swap is accepted

- Status: accepted
- Date: 2026-10-26

## Context

Coupon codes are 12 random Crockford Base32 characters plus one check character (§8.1). The
check character lets the dealer app reject mistyped or misread codes on the device, without a
network call (§18.2 rule 3). Luhn mod N (ISO/IEC 7812 generalised) catches every single-character
error. It also catches every adjacent transposition but one.

In Luhn mod 32, a doubled code point `v` contributes `⌊2v/32⌋ + (2v mod 32)`. For `v = 0` that
is 0, and for `v = 31` (`Z`) it is `1 + 30 = 31`. Both are fixed points, so swapping an adjacent
`0` and `Z` does not change the sum. This is the same limit as the familiar `09 ↔ 90` blind spot
in decimal Luhn.

## Decision

Use Luhn mod 32 anyway and document the blind spot:

- `packages/shared/src/luhn32.ts` and `public.luhn32_check_char()` implement the same algorithm.
  They are verified against 1,000 shared vectors (`packages/shared/test-vectors/luhn32.json` →
  `supabase/tests/005_luhn_vectors.test.sql`, generated by `pnpm --filter @24m/shared vectors`).
- The property test asserts that every adjacent transposition is detected **except** `0↔Z`.

## Why not something stronger

- Damm or Verhoeff over 32 symbols catch every transposition, but they need a 32×32 table that
  must be identical in TS and SQL. That is harder to review and gains only one pair.
- A swapped code still has to exist in the database, be ACTIVE and belong to the dealer's
  scope. A random 12-character payload has 32¹² ≈ 1.15 × 10¹⁸ combinations, so a valid
  neighbour is negligible. The server is the real guard; the check character only saves a round
  trip.
